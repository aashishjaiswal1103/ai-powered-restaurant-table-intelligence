# Restaurant AI Operations System — MVP Tech Stack

> **Purpose:** This document is the technical source of truth for AI coding assistants working on the MVP. Follow the stack and architecture below unless the project owner explicitly changes a decision.

## 1. Product Scope

Build an **AI-powered restaurant operations system** with:

- Existing restaurant CCTV/RTSP video input.
- Computer-vision-based table occupancy detection.
- Table-level lifecycle tracking.
- QR-based customer self-ordering.
- One central manager dashboard for table status and incoming orders.
- Persistent table-cycle, event, and order history in RushDB.

### Explicitly out of scope for this MVP

- Separate kitchen dashboard.
- Waiter/staff mobile application.
- Customer order tracking interface.
- POS integration.
- Online payments.
- Facial recognition or customer identity tracking.
- Predictive customer-departure AI.
- Inventory management.
- Multi-restaurant SaaS administration.

All submitted QR orders are shown on the **central manager dashboard**.

## 3. High-Level Architecture

```text
Existing CCTV / RTSP stream / recorded MP4
                  |
                  v
       Video Ingestion Pipeline
          OpenCV + FFmpeg
                  |
                  v
        Computer Vision Pipeline
          YOLO + ByteTrack
                  |
                  v
       Table Association Engine
   Person tracks -> configured table zones
                  |
                  v
       Table Lifecycle Engine
   Occupancy -> Arrival -> Departure
       -> Cleaning -> Available
                  |
                  v
             FastAPI
       REST API + WebSockets
          /             \
         v               v
      RushDB       React Frontend
   Persistent data   Manager Dashboard
                     Customer QR Menu
```

### Architectural responsibilities

- **Computer vision worker:** Reads video, detects/tracks people, associates tracks with table zones, and produces occupancy observations.
- **Table lifecycle engine:** Converts observations and business actions into validated state transitions and lifecycle events.
- **FastAPI backend:** Exposes APIs, handles QR orders, coordinates lifecycle operations, and broadcasts real-time updates.
- **RushDB:** Stores persistent entities, relationships, cycles, events, menu data, and orders.
- **React frontend:** Displays annotated camera video, table states, incoming orders, and historical analytics.

Keep computer vision processing separate from HTTP request handling. Do not run a blocking, continuous video loop inside a normal API request.

## 4. Table Lifecycle

Each table follows this intended lifecycle:

```text
FREE
  -> GUEST_ARRIVED
  -> ORDERED
  -> GUEST_DINING
  -> GUEST_LEFT
  -> CLEANED
  -> FREE
```

### State/event semantics

| Lifecycle stage | Source | Meaning |
|---|---|---|
| FREE | System/staff-confirmed | Table is ready for customers |
| GUEST_ARRIVED | Computer vision observation, optionally staff-confirmed | Guests are seated |
| ORDERED | QR ordering transaction | At least one order was submitted |
| GUEST_DINING | Lifecycle logic | Guests are dining |
| GUEST_LEFT | Computer vision observation, optionally staff-confirmed | Guests have departed |
| CLEANED | Manager/staff action | Cleaning is confirmed complete |
| FREE | Lifecycle engine | Cycle is closed; table is available again |

### Important rules

- Arrival and departure are **computer-vision observations**, not absolute truth. Use thresholds, temporal smoothing, and recovery logic.
- `ORDERED` must be generated by a successful order submission, not inferred from CCTV.
- Cleaning completion must be explicitly confirmed by a manager/staff action.
- A table may receive multiple orders during one cycle.
- Do not start a second active cycle for a table that already has one.
- Every completed cycle must remain in history.
- Distinguish AI-observed events, customer-generated transactions, and staff-confirmed events.
- Handle temporary camera disconnections and detection failures without immediately closing a cycle.

## 5. Persistent Data Model — RushDB

Represent the following logical entities and relationships in RushDB. Use RushDB-supported record and relationship mechanisms; do not assume relational SQL tables.

### Restaurant

Suggested fields:

- `restaurant_id`
- `name`
- `timezone`
- `created_at`

### Camera

Suggested fields:

- `camera_id`
- `name`
- `source_type` (`rtsp` or `file`)
- `source_reference` (secure configuration reference; never expose credentials)
- `status`
- `created_at`

### Table

Suggested fields:

- `table_id`
- `display_name`
- `capacity`
- `camera_id`
- `zone_polygon`
- `current_state`
- `current_cycle_id`
- `created_at`

### TableCycle

One record represents one complete customer visit/table-use cycle.

Suggested fields:

- `cycle_id`
- `table_id`

- `first_order_at`
- `departure_at`
- `cleaned_at`
- `closed_at`

### TableEvent

Suggested fields:

- `event_type`

### MenuCategory

Suggested fields:

- `category_id`
- `restaurant_id`
- `name`
- `display_order`
- `active`

### MenuItem

Suggested fields:

- `item_id`
- `restaurant_id`
- `category_id`
- `name`
- `description`
- `price`
- `image_reference`
- `available`

### Order

Suggested fields:

- `order_id`
- `restaurant_id`
- `table_id`
- `cycle_id`
- `items`
- `subtotal`
- `total`
- `status`
- `submitted_at`
- `acknowledged_at`

### Relationships

Maintain the logical relationships:

```text
Restaurant -> Cameras
Restaurant -> Tables
Restaurant -> Menu Categories
Restaurant -> Menu Items
Table -> Table Cycles
Table Cycle -> Table Events
Table Cycle -> Orders
Menu Category -> Menu Items
Order -> Ordered Menu Items (or embedded item snapshots)
```

**Order items should preserve a snapshot of the item name and price at submission time**, so historical orders remain accurate if the menu changes later.

### Persistence rules

- Persist lifecycle events and completed cycles.
- Persist orders and order-item snapshots.
- Persist table configuration and table-zone coordinates.
- Do not persist every video frame or every raw detection.
- Keep high-frequency tracking state in process memory.
- Persist meaningful state changes and operational events.
- Use unique event and cycle identifiers.
- Make order submission idempotent to avoid duplicate orders on retries.
- Do not claim a database write succeeded until RushDB confirms it.

## 6. Computer Vision Pipeline

### Input

Support:

- Recorded MP4 video for development and testing.
- RTSP streams from existing IP CCTV cameras.

### Processing

1. Read frames using OpenCV/FFmpeg.
2. Apply an appropriate frame sampling rate.
3. Run YOLO person detection.
4. Run ByteTrack tracking.
5. Calculate person footpoints (bottom-center of bounding boxes).
6. Associate tracked people with configured table polygons.
7. Aggregate observations per table.
8. Apply temporal smoothing and occupancy thresholds.
9. Emit occupancy observations/state-transition events.
10. Draw table overlays on the processed frame.

### Table zones

- Tables are configured manually as polygons on a camera frame.
- Table IDs remain stable across frames.
- Use polygon geometry for point-in-region association.
- Do not assume bounding-box overlap alone is sufficient for occupancy.
- Avoid counting passersby as seated guests.
- Camera angle, occlusion, and overhead footage may require different association strategies.

### Annotated video

Show:

- Table ID.
- FREE/OCCUPIED or relevant lifecycle status.
- Estimated people count.
- Occupancy duration.
- Bounding box or polygon around the table.

The annotation must represent table regions, not confuse them with person-detection boxes.

## 7. QR Ordering Flow

### Customer experience

1. Customer scans the QR code on a table.
2. A mobile-friendly menu opens in the browser.
3. The URL identifies the restaurant and table using a validated table token.
4. Customer browses menu categories and items.
5. Customer adds items to a cart.
6. Customer submits an order.
7. Backend validates menu availability and prices.
8. Backend creates the order and associates it with the table's active cycle.
9. The manager dashboard receives the order through WebSockets.
10. Customer sees a basic submission confirmation.

### MVP order scope

- Table-specific QR codes.
- Mobile-friendly menu.
- Menu categories.
- Item details and prices.
- Cart and quantity changes.
- Order submission.
- Multiple orders per cycle.
- Manager order acknowledgment.
- Cash/payment-at-counter assumption.

### Explicit exclusions

- Kitchen order dashboard.
- Waiter application.
- Customer order-tracking interface.
- Online payment gateway.
- POS integration.
- Customer registration.

### Security and correctness

- Validate table tokens server-side.
- Never trust client-submitted prices or totals.
- Calculate totals on the backend from current menu data.
- Preserve menu item name and price snapshots in order records.
- Prevent duplicate order submission with idempotency handling.
- Do not expose camera credentials or RushDB API credentials to the browser.

## 10. Real-Time Communication

Use WebSockets to push updates from FastAPI to the manager dashboard.

Events may include:

```text
table.state_changed
table.guest_arrived
table.guest_left
table.cleaned
cycle.completed
order.submitted
order.acknowledged
camera.status_changed
```

WebSockets are for real-time notifications, not persistent storage. RushDB remains the persistence layer.

On dashboard reconnection, fetch the authoritative current state from the backend.

## 12. Engineering Principles for the AI Coding Assistant

1. **Respect the selected stack.** Do not replace RushDB with SQLite or another database.
2. **Keep the MVP scope narrow.** Do not introduce kitchen dashboards, customer tracking, POS, or payments.
3. **Separate concerns.** Video processing, lifecycle logic, ordering, persistence, and UI should have clear boundaries.
4. **Use event-driven lifecycle logic.** Every state transition should produce an identifiable event.
5. **Treat CV output as uncertain.** Use confidence, smoothing, and recovery logic.
6. **Validate all backend operations.** Never rely exclusively on frontend validation.
7. **Protect secrets.** Camera credentials and database API keys stay server-side.
8. **Keep historical data immutable where practical.** Completed cycles and order snapshots should not be silently overwritten.
9. **Avoid unnecessary infrastructure.** No microservices, Kubernetes, Kafka, or Redis in the initial MVP.
10. **Write testable modules.** Test lifecycle transitions, ordering validation, table association, and duplicate-order handling independently.
11. **Do not fabricate RushDB SDK methods.** Verify the installed SDK/API documentation before implementing database operations.
12. **Document architectural changes.** Update this file when an explicitly approved technology or product decision changes.

## 13. MVP Completion Criteria

The MVP is demonstrably working when:

- A recorded video can be processed.
- One live RTSP camera can be connected.
- Table polygons can be configured.
- People can be detected and tracked.
- Table occupancy can be estimated and displayed.
- Arrival and departure events are generated with reasonable stability.
- A complete table cycle can be created and closed.
- A table-specific QR menu can be opened on a phone.
- A customer can submit an order.
- The order appears on the manager dashboard.
- The order is linked to the correct table cycle.
- Cleaning can be confirmed by the manager.
- Completed cycles, lifecycle events, and orders persist in RushDB.
- The dashboard can display current states and historical cycles.
